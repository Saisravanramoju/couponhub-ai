# Architecture and boundaries

## Persistence and authorization

The existing .NET 9 Clean Architecture solution remains the base. EF Core applies an owner filter to every normal coupon query: public rows (`owner_id IS NULL`) plus the current account's rows. Admins can manage public coupons and their own imports, but cannot inspect other users' private imports through these endpoints. Every mutation checks ownership or admin role. New coupons are always private, including administrator imports, until explicitly published.

Accounts use ASP.NET Core's password hasher. Sessions contain 256 random bits; only a SHA-256 hash is stored server-side. Android encrypts the session with an Android Keystore AES-GCM key and disables app backups. Logout revokes the current server token and clears local cache, reminders and session state. The Room coupon cache is app-private storage, not an encrypted database, and cached coupons are labeled stale when offline.

The new PostgreSQL migration adds accounts, sessions, saved coupons, event history and nullable coupon ownership. It preserves existing public rows. It normalizes legacy codes to uppercase; conflicting case variants cause a transactional migration failure, rather than deleting an existing coupon. Resolve such duplicates explicitly before retrying. Downgrade refuses to make private coupons public by silently dropping ownership.

## AI boundary

Only user-selected offer text or a bounded shortlist of coupon descriptions is sent to OpenAI after an explicit UI opt-in. No password, session token, account email, complete inbox or raw screenshot is sent. The backend key stays on the server. Inputs and model outputs are untrusted. The provider adapter requests JSON mode, rejects incomplete/refused responses and filters returned recommendation IDs against the original shortlist. Coupon policy and eligibility remain deterministic.

The provider adapter is an application interface and can be replaced with Azure OpenAI or another implementation. This delivery wires the OpenAI provider only; it does not advertise unimplemented provider choices in the app.

## Operational limits and further product work

This is a runnable-source MVP, not a claim of production certification or measured availability/latency:

- No live partner/affiliate feeds or background email-account integration are configured. Email and notification imports are explicitly pasted by the user. No merchant app UI scraping or passive notification capture occurs.
- Search is text/category matching plus optional model ranking over a shortlist. Embedding storage, vector retrieval and corpus-wide semantic search are future extensions.
- Saved coupons provide the current behavioral signal. Copy/use events are stored, but no trained recommender or fraud-resistant redemption verification is claimed.
- Reminders are Android background work; scheduling depends on Android battery/network policies. New-offer push notifications and an email notification service are not included.
- Account verification, password reset, all-session revocation UI, MFA and user account deletion/export flows need a dedicated production identity design.
- Rate limits are per API instance; distributed rate limiting, pagination of the legacy GET-all endpoints, retention policies for event/session data, telemetry and capacity tests remain deployment work.
- No Play Store signing/publishing or cloud deployment was requested/performed. A debug APK is generated by CI only after Android checks pass.

The app is intentionally explicit about optional AI and stale/offline information. No production SLA, recommendation quality metric or merchant redemption success rate has been measured.
